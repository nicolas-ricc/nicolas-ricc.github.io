# `pdf` only in the cv zone (#202) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `subagent-driven-development` (`.agents/skills/subagent-driven-development/SKILL.md`) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `validateContent` rejects a `pdf` field on any zone other than `cv`, so the CV-specific labels hard-coded in `renderPdf` can never end up on a Portfolio or Blog PDF.

**Architecture:** one extra rule in `src/content/validate.ts`, next to the existing `pdf` type check. The repo's content JSON files are validated by the test `"los JSON del repo son válidos"` in `src/content/validate.test.ts`, which CI runs (`.github/workflows/deploy.yml`, `npm test`), and by `npm run validate` (`scripts/validate-content.ts`, not run in CI). Neither the site nor the build calls `validateContent`, so these two are the gates that stop a non-cv `pdf` from landing. Comments on `ZoneContent.pdf` and on `renderPdf` record why the labels may stay hard-coded.

**Tech Stack:** TypeScript strict, Vitest (`npm test`), `tsc --noEmit` (`npm run typecheck`).

**Spec:** issue #202 (follow-up of #193), plus the owner's decision comment of 2026-11-01: "`validate.ts` acepta `pdf` sólo en la zona cv, con test; no se agrega `pdfLabel` al JSON. Código, comentarios y mensajes de test nuevos, en inglés (ver #194)."

## Global Constraints

- Files that change: `src/content/validate.ts`, `src/content/validate.test.ts`, `src/content/types.ts` (comment only), `src/content/render.ts` (comment only).
- No `pdfLabel` and no other new field in the content JSON or in `ZoneContent`. The strings in `renderPdf` stay as they are.
- New code, comments, error messages and test names are written in English (#194). Existing Spanish messages and tests stay as they are.
- Commits use `<type>(#202): ...`. `npm test` and `npm run typecheck` stay green.
- Evals stage of the pipeline: the failing tests of Task 1 Step 1 are committed as `test(#202): evals` before implementation, and the implementer starts at Step 3.

## Technical decisions (declared)

1. **Exact error string:** `"pdf: only the cv zone may declare one"`. It follows the existing `"<path>: <problem>"` format, so it starts with `pdf`.
2. **The zone check is independent of the type check.** Any `pdf !== undefined` on a zone whose `id !== "cv"` is an error, whatever its type. A non-string `pdf` on a non-cv zone yields both errors, type error first. An invalid or missing `id` together with a `pdf` also yields the zone error, because that zone is not cv.
3. **`pdf` stays optional for cv.** A cv zone without `pdf` is still valid. The issue only restricts where the field may appear.
4. **No runtime check in `render.ts`.** Validation is where the owner put the rule, and render keeps its labels. A comment in `renderPdf` points at the rule.

## Spec → tasks

- "restrict `pdf` to the `cv` zone in `validate.ts`" and "con test" → Task 1.
- "no se agrega `pdfLabel`" → Global Constraints. No task touches the JSON.

## Review Focus

1. A Portfolio or Blog zone that is otherwise valid and declares `pdf: "/x.pdf"` must give exactly one error, the zone error. Task 1 test, which covers both zones.
2. A cv zone must keep accepting `pdf`, and a cv zone without `pdf` must stay valid. Task 1 test.
3. A non-cv zone with an empty or non-string `pdf` (`""`, `3`) must not slip through because of the type check. Task 1 test expects both errors.
4. The real `content/*.json` must still validate, so `cv.json` keeps its `pdf` and the others carry none. This is covered by the existing test `"los JSON del repo son válidos"`, unchanged.
5. A `pdf` present with an invalid or missing `id` must not silently pass. Task 1 test.

- [ ] **Step 1: Write the failing tests** (new block in `src/content/validate.test.ts`, which reuses the file's `ok` fixture, whose zone is portfolio)

```ts
describe("validateContent: pdf", () => {
  const cvZone = { id: "cv", titulo: "CV", secciones: [] };
  it("accepts a pdf on the cv zone, and a cv zone without one", () => {
    expect(validateContent({ ...cvZone, pdf: "/cv.pdf" })).toEqual([]);
    expect(validateContent(cvZone)).toEqual([]);
  });
  it("rejects a pdf on any other zone", () => {
    for (const id of ["portfolio", "blog"]) {
      expect(validateContent({ ...ok, id, pdf: "/x.pdf" })).toEqual(["pdf: only the cv zone may declare one"]);
    }
  });
  it("reports both the type and the zone of a bad pdf outside cv", () => {
    for (const pdf of ["", 3]) {
      expect(validateContent({ ...ok, pdf })).toEqual(["pdf: no es string", "pdf: only the cv zone may declare one"]);
    }
  });
  it("rejects a pdf whose zone id is unknown or missing", () => {
    expect(validateContent({ ...ok, id: "nada", pdf: "/x.pdf" })).toContain("pdf: only the cv zone may declare one");
    const { id: _, ...noId } = ok;
    expect(validateContent({ ...noId, pdf: "/x.pdf" })).toContain("pdf: only the cv zone may declare one");
  });
});
```

- [ ] **Step 2: Run them to verify they fail**

Run: `npx vitest run src/content/validate.test.ts`
Expected: "rejects a pdf on any other zone", "reports both…" and "rejects a pdf whose zone id is unknown or missing" FAIL because the zone error is missing. "accepts a pdf on the cv zone…" and every existing test PASS.

- [ ] **Step 3: Implement**

## Assumptions

- **A typed `PDF_ZONE: ZoneId` constant instead of a bare `"cv"` literal.** The rejected alternative is the inline literal. The constant makes a rename of the zone union (`src/map/zones.ts:1`) fail typecheck instead of drifting silently. (Grilling Q2)
- **`cvZone` in the test is hand-built in the shape of `content/cv.json`** (`secciones: []`, no other fields), not derived from `ok`. The rejected alternative is `{ ...ok, id: "cv" }`, which carries portfolio-style sections that the real cv never has. (Q5)
- **The evals commit carries the test file, and Step 5 commits only the implementation.** This follows the pipeline order declared in Global Constraints. (Q9)
